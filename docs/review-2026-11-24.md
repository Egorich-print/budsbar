# BudsBar — engineering review, 24 November 2026

Reviewer: automated engineering review of the public repository
<https://github.com/Egorich-print/budsbar> at commit `4c3d768` (branch `main`). Target machine:
macOS 27.2.1 (build 26B131), arm64, Xcode 27.2 (27B52), Swift 6.4.2 (swiftlang-6.4.2.1.9).

---

## 1. Summary

BudsBar is a native macOS menu-bar panel that controls HUAWEI FreeBuds earbuds directly over the
Bluetooth Serial Port Profile, without the vendor app. The protocol layer (`Sources/BudsCore`) is
genuinely good: the frame codec, the CRC, the command ids and the ANC write payloads all match four
independent implementations byte for byte. The defects are concentrated in three places — the
correlation of asynchronous responses, the mapping of TLV tags onto fields, and the
release/packaging pipeline. The single most urgent item is not a bug at all: the repository is
public and it carries the owner's real device serial number in the initial commit, in the unit-test
fixture and — rendered as pixels — in all three committed screenshots. The fork
`felipecastro009/budsbar` inherited the images and the original commits, so the data now lives in
two public repositories. Everything else in this report can wait a release cycle; that cannot.

| Area | State | Findings |
|---|---|---|
| Protocol core | Builds, tests green; codec and command map verified against four independent implementations | 8 critical (C1–C8), including 2 async-correlation defects, 4 tag-mapping defects and 1 protocol-documentation defect |
| UI panel | Renders correctly, but reports values the device never sent | 13 major (M1–M13) |
| Build / CI / Release | `swift build` and `swift test` pass locally; CI artifacts are mislabelled and unsigned | M1, M3, M4, M5 |
| Documentation | `PROTOCOL.md`, `DESIGN.md`, `MOTION.md`, `README.md` all drift from the code | 8 drift items (§8) |
| External cross-check | The wire format is confirmed; the project's own protocol notes disagree with the code about one field | 9 confirmations (§5), 4 gaps (§6), 1 documentation defect (C5) |
| Runtime verification | No live protocol read was possible — the earbuds are paired but not connected | Protocol conclusions rest on code, captured frames and independent implementations |

## 3. Critical findings

### C1. **[CRITICAL] Real device serial numbers are published in a public repository**

**What happens.** The owner's physical device identifiers are committed to a public GitHub
repository in three places, and one of them is rendered as pixels in the screenshots the README
displays.

- `Sources/BudsPanelShot/main.swift:69` — `state.identity.serialNumber =
"3EDB…2105"`, the real device serial, hard-coded in the preview renderer.
- `Tests/BudsCoreTests/BudsCoreTests.swift:23-27` — a captured device-info
frame. Decoded, tag `0x09` carries the device serial `3EDB…2105`, tag `0x18` carries the per-side
serials `L-…892` and `R-…134`, tag `0x0A` carries the product id.
- `docs/research/PROTOCOL.md:139` — the product id `BTFT0020-…155`.
- `docs/images/panel-connected.png`, `docs/images/panel-cancelling.png` and
`docs/images/panel-connecting.png` — the "Serial" row of the Device section is legible in all three
images. The PNGs are 640×1286, 640×1356 and 640×1286 pixels, i.e. 2× renderings of a 320 pt panel.

The local `backups/` directory holds two further copies of the same file with the same serial
(`backups/2026-10-28-codec-row/Sources/BudsPanelShot/main.swift`,
`backups/2026-10-28-panel-height/main.swift`). They are **not** tracked by git — `backups/` is
listed in `.gitignore:2` and `git ls-files backups` is empty — so they are not part of the published
history, but they must not be added to it either.

All of it entered the repository with the initial commit `6f5bac0` and is therefore reachable at
<https://github.com/Egorich-print/budsbar>.

**Why it matters.** A device serial number is a stable physical identifier. It ties the owner's
Huawei account, warranty record and retail purchase to a public GitHub identity, and it is a value
that cannot be rotated the way a password can. The damage is already published; fixing the current
tree does not unpublish it. Anyone who scrapes GitHub has it.

**How to fix.** Treat this as a red line and rewrite history — see §9, S1. Concretely: rewrite the
history with `git filter-repo` (or BFG), force-push, ask GitHub Support to purge the cached views of
the affected blobs, replace the serial in the test fixture with a synthetic one, re-render all three
PNGs with a synthetic serial through `scripts/render-panel.sh`, and delete the local `backups/`
snapshots from disk. Keep a note of the old-to-new mapping somewhere outside the repository.

### C2. **[CRITICAL] The device error marker (tag 127) is never decoded**

**What happens.** `docs/research/PROTOCOL.md:61` documents tag 127 with the value `00 01 86 a3` as
the "unsupported command" marker, and `docs/research/PROTOCOL.md:154-157` records that a sweep of
the command range returned only that marker. The code has no notion of it at all:

- `Sources/BudsCore/Commands.swift:227-234` — the `Tag` enum defines 1, 2, 3,
4, 5 and 6. There is no 127.
- `Sources/BudsCore/DeviceController.swift:101-120` — `handle(_:)` matches on
command id only; a frame carrying tag 127 is silently discarded.
- `Sources/BudsCore/DeviceController.swift:271-310` — `apply(_:)` has no 127
branch.

`Sources/BudsCore/WireFormat.swift:129` stores unknown tags faithfully, so the marker is parsed and
then thrown away.

**Why it matters.** "This command is not supported" becomes indistinguishable from "there is no
data". A read the device refuses returns a frame that the controller treats as a successful empty
answer: the state is not updated and no error is shown. A write the device refuses ends at
`Sources/BudsCore/DeviceController.swift:235` with "The earbuds did not confirm the change." — after
a full timeout — because the app never learns *why*. The user is told the earbuds did not answer,
when in fact the earbuds answered with an explicit refusal.

**How to fix.** Add `Tag.error = 127` to `Sources/BudsCore/Commands.swift:227-234`, check for it at
the top of `handle(_:)` (`DeviceController.swift:101`), and turn it into a typed error
(`TransportError.unsupportedCommand`) that `read(_:)` and `apply(_:)` surface. Then the refusal
becomes a one-line message instead of a timeout, and a command that a given model does not implement
can be skipped instead of retried forever.

### C3. **[CRITICAL] The answer to a write is correlated against the wrong command id**

**What happens.** `Sources/BudsCore/DeviceController.swift:196` registers the waiter for
`verify.command` — the *read* command id — and expects the device's answer to the write to arrive on
that id:

```swift
let waiter = Task { try await self.waitForFrame(verify.command) }
```

But the device answers a write on the *write* command id (`docs/research/PROTOCOL.md:80-81`: "Read
commands answer on the same command id. Write commands answer on the write command id and are
followed by the device pushing current state."). The write answer therefore matches neither the
waiter (`0x2B2A`) nor any entry in `pending` (which only holds read commands), so it falls through
every branch of `handle(_:)` (`Sources/BudsCore/DeviceController.swift:101-120`) and is dropped.

That the device really does answer on the write id is confirmed by an independent implementation:
the omarchy bridge carries a hard-coded write acknowledgement frame `5A0006002B040201003171` —
command `0x2B04`, tag 2 = `00` — and rejects any other pairing as `unexpected_response`
(<https://github.com/filipechagas/omarchy-huawei-freebuds>).

**Why it matters.** The frame that carries the device's verdict on a write is never seen by the code
that needs it. In particular the tag-127 error marker (C2) arrives on the write id, so C2 and C3
compound: the one frame that could explain a refusal is the one frame that is thrown away.

**How to fix.** Register the waiter for the write command id (`request.command`), and treat the
subsequent read as the verification step. Concretely: wait for `request.command`, then poll the read
until `matches(_:request:)` holds, with the existing two-attempt fallback at
`DeviceController.swift:226-234` repurposed as the verification loop rather than as a substitute for
the missing answer.

### C4. **[CRITICAL] Races in the pending/waiter bookkeeping**

**What happens.** Four separate places assume that a command id identifies a unique outstanding
request. It does not.

- `Sources/BudsCore/DeviceController.swift:167` — on a write failure,
`pending.removeAll { $0.command == request.command }` removes **every** pending entry with that
command id, including entries owned by other tasks. Those continuations are never resumed.
- `Sources/BudsCore/DeviceController.swift:129-131` — the timeout task takes
`removeFirst()` from the waiter array for that command id. The first waiter is not necessarily the
one the timeout was created for.
- `Sources/BudsCore/DeviceController.swift:174-176` — the read timeout takes
`firstIndex(where: { $0.command == request.command })`, i.e. the first matching pending entry, again
not necessarily the one that timed out.

**Why it matters.** A foreign request can be failed prematurely by another request's timeout, while
the task that owns it is left with an unresolved `CheckedContinuation`. When such a task is
deallocated the runtime reports `SWIFT TASK CONTINUATION MISUSE` and the process traps. The window
is real: `refresh()` is serial (`DeviceController.swift:149-156`), but the 20-second poll
(`DeviceController.swift:92-94`), the manual refresh button
(`Sources/BudsUI/ControlPanel.swift:302-305`) and a user write
(`Sources/BudsUI/PanelContent.swift:230`) can overlap, and the panel is a `MenuBarExtra` whose
content can be re-created at any time.

**How to fix.** Correlate on a per-request token, not on the command id. Give each request a
monotonically increasing id, store it in `PendingRequest` and in the waiter entry, and have the
timeout task remove *its own* entry by token (`removeAll { $0.token == token }` scoped to the exact
entry) rather than by command. The same token must be carried by the frame that satisfies it, which
means the correlation must move from "command id" to "FIFO order per command" — see §9, S3.

### C5. **[CRITICAL] The protocol notes misdescribe the ANC answer, and the level byte is never verified**

**What happens.** `Sources/BudsCore/DeviceController.swift:277-281` decodes the `0x2B2A` answer as
`[level, mode]`:

```swift
state.cancellationLevel = Int(value[0])
state.noiseMode = NoiseMode(rawValue: Int(value[1]))
```

`docs/research/PROTOCOL.md:88` and `:106-109` say something different — that the first byte is the
*effect* the firmware reports (1 off / 2 transparency / 3 cancelling) and that "the device never
reports how strong the cancellation is, so the strength cannot be read back".

Three independent implementations and the captured frames settle the question, and they side with
the **code**:

| Source | Statement | URL |
|---|---|---|
| freebuds-client | "byte 0 = código do nível / byte 1 = código do modo" (§4.3) | <https://github.com/hrbtnog/freebuds-client> |
| OpenFreebuds | `self.active_mode = data[1]`; `cancel_level_options.get(data[0], data[0])` | <https://github.com/MelianMiko/OpenFreebuds> |
| omarchy bridge | `mode = _ANC_MODE_NAMES.get(state[1])` — the mode is the second byte; the first is the level | <https://github.com/filipechagas/omarchy-huawei-freebuds> |

The three ANC read frames published by the omarchy bridge decode exactly that way, and the
project's own mode enum agrees with them byte for byte:

| Frame (tag 1 payload) | Level (byte 0) | Mode (byte 1) | Project's `NoiseMode(rawValue: value[1])` |
|---|---|---|---|
| `00 00` — ANC off | 0 | 0 | `.off` ✓ |
| `03 01` — ANC on | 3 (dynamic) | 1 | `.cancellation` ✓ |
| `02 02` — awareness | 2 | 2 | `.awareness` ✓ |

The documented byte values cannot be right either: `docs/research/PROTOCOL.md:106-109` says the
effect byte is `1` when noise control is off, but the captured off frame carries `00`.

**Why it matters.** The decoding is correct; the documentation and the reasoning built on top of
it are not. Three consequences:

- `docs/research/PROTOCOL.md:110-117` concludes that on the FreeBuds 6 "the firmware accepts the
  strength byte but does not apply it". An independent test on the same model contradicts this —
  see F1 in §6. The conclusion that led to the wrong capability table came from the misreading, not
  from the device.
- `Sources/BudsCore/DeviceCapabilities.swift:41-52` excludes level 2 for FreeBuds 6 "the deepest
  cancellation level is not implemented". The outcome is accidentally right (Gadgetbridge found the
  same: ultra has no audible effect) but the stated reason is wrong, and no reader can tell the
  difference.
- `matches(_:request:)` at `Sources/BudsCore/DeviceController.swift:242-245` verifies only the mode
  byte:

  ```swift
  return value[1] == wanted   // wanted = request.fields[Tag.left]?.first = the requested mode
  ```

  A mode change is therefore verified correctly, but a **level** change is not verified at all:
  `setNoiseMode(_:level:)` writes `[mode, strength]`, the read-back carries the new level in byte 0,
  and the comparison never looks at byte 0. The write reports success on the strength byte it never
  checked — the one thing `README.md:27-29` promises never happens.

**How to fix.** Correct `docs/research/PROTOCOL.md:88`, `:106-109` and `:110-117` to `[level, mode]`
and to the finding in F1, and re-justify `Sources/BudsCore/DeviceCapabilities.swift:41-52` on the
evidence from #7339. Then extend `matches()` so that a request carrying a strength byte also
verifies byte 0 of the answer, and a request without one ignores it.

### C6. **[CRITICAL] The charging flags are read from a tag that does not carry them**

**What happens.** `docs/research/PROTOCOL.md:86` and `Sources/BudsCore/DeviceController.swift:333`
read the charging flags from tag 6, requiring three bytes:

```swift
if let flags = frame.fields[Tag.charging], flags.count >= 3 {
```

The battery read at `Sources/BudsCore/Commands.swift:240` asks for tags `[1, 2, 3]`. The
battery frame published by the omarchy bridge — captured from a FreeBuds Pro 5, not from the
FreeBuds 6 this project targets — decodes as:

```
5A 00 1B 00 01 08 01 01 64 02 03 64 64 55 03 03 00 00 00 04 02 0A 14 05 02 00 01 06 01 0A 4D 9B
```

Decoded: tag 1 = `64` (global level), tag 2 = `64 64 55` (left / right / case), **tag 3 = three
bytes** `00 00 00`, tag 4 = `0A 14`, tag 5 = `00 01`, **tag 6 = a single byte** `0A`.

Both independent implementations read the charging flags from tag 3: OpenFreebuds' battery handler
uses `package.parameters[3]` and checks for the byte `0x01`; freebuds-client's protocol document
lists parameter 3 as the charging flags and parameter 6 as "1 byte, unknown, observed `0A`".

**Why it matters.** `flags.count >= 3` can never be satisfied by a one-byte tag 6, so
`state.isChargingLeft`, `isChargingRight` and `isChargingCase`
(`Sources/BudsCore/DeviceState.swift:113-115`) are never set to `true`. The charging indicators in
`Sources/BudsUI/PanelContent.swift:44-56` never light up, and the panel does not distinguish a full
case from a charging one.

**How to fix.** Read the flags from tag 3 and drop the `count >= 3` requirement in favour of a
per-component interpretation with an explicit unknown state. This one must be confirmed against a
live device that is actually charging before the mapping of the three bytes to left / right / case
is hard-coded — freebuds-client is explicit that this mapping is still a hypothesis on its hardware,
too.

### C7. **[CRITICAL] The serial number and the product id are read from the wrong fields**

**What happens.** `Sources/BudsCore/Commands.swift:239` requests device-info tags `[3, 7, 10, 15,
24]` — build id, firmware, product id, model code and the per-side serials. Tag 9 is **not
requested**.

`Sources/BudsCore/DeviceController.swift:312-325` then does:

| Line | Assignment | Problem |
|---|---|---|
| `:316` | `state.identity.serialNumber = frame.text(9)` | Tag 9 is never requested → the value is always `nil` |
| `:317` | `state.identity.leftSerial = frame.text(10)` | Tag 10 is the *product id*, not a serial |
| `:318-324` | Tag 24 is split on `,` into `leftSerial` / `rightSerial` | Correct data, but it overwrites the product id that was put in `leftSerial` |

The project's own protocol table is right and the code is wrong: `docs/research/PROTOCOL.md:85`
lists "9 = serial, 10 = product id, 15 = model code, 24 = per-side serials". freebuds-client's
device-info table agrees (`0x09` serial_number, `0x0A` device_submodel, `0x0F` device_model, `0x18`
serial L/R).

**Why it matters.** The "Serial" row of the Device section (`Sources/BudsUI/PanelContent.swift:169`)
is permanently "—", because `identity.serialNumber` can never be populated.
`DeviceIdentity.leftSerial` and `rightSerial` are populated from tag 24, but no view shows them, so
the per-side serials that the device does report are dropped on the floor. The product id, which the
device does report, is read into the wrong field and then overwritten.

**How to fix.** Add tag 9 to the request at `Sources/BudsCore/Commands.swift:239`, read the product
id into its own field on `Sources/BudsCore/DeviceState.swift:39-41`, and surface the per-side
serials in the Device section. Note that the request list should arguably be widened to
`0x00...0x1F` in one shot, the way freebuds-client and OpenFreebuds do it —
`Sources/BudsCore/RFCommLink.swift` already has no constraint against it and it would remove the
whole class of "tag X was never requested" bugs.

### C8. **[CRITICAL] Signed bytes corrupt the gesture action code 255 ("Do Nothing")**

**What happens.** `Sources/BudsCore/WireFormat.swift:66-70` decodes a tag value as a list of
**signed** bytes:

```swift
public func byteList(_ tag: UInt8) -> [Int]? { ... return value.map { Int(Int8(bitPattern: $0)) } }
```

The available-action lists are read through it at `Sources/BudsCore/DeviceController.swift:292`
(tap) and `:299` (hold). The firmware advertises `255` as a valid action —
`docs/research/PROTOCOL.md:141` ("Tap actions | 1 play/pause, 2 next, 7 previous, 0 assistant, 255
none") and `docs/research/PROTOCOL.md:120-125` (the hold list ends in `255`). `0xFF` decoded as
`Int8` is `-1`.

**Why it matters.** Two failures in one:

- The picker shows a nonsense entry. `GestureAction.title(for:)`
(`Sources/BudsCore/Commands.swift:130-132`) renders it as "Action −1", and `GestureAction(rawValue:
-1)` is `nil`, so the entry has no name.
- Selecting it writes the wrong action to the earbuds.
`Sources/BudsCore/Commands.swift:289` does `UInt8(clamping: action)`, and `UInt8(clamping: -1)` is
`0` — **"Voice Assistant"**. The user picks "Do Nothing" and gets the voice assistant.
- The fallback list compounds it. `Sources/BudsUI/ControlPanel.swift:434` uses
`[-1, 0, 1, 2, 7, 255]` when the device advertises nothing, and
`Sources/BudsUI/ControlPanel.swift:426` uses `-1` as the "nothing selected" sentinel (`value ??
-1`). The corrupted 255 and the sentinel are the same value, so the two cannot be distinguished.

**How to fix.** Make `byteList` unsigned — `Int($0)` — and audit its callers. The `Int8` conversion
was presumably added for a signed "level" field that does not exist in this protocol. Then change
the sentinel from `-1` to `nil`/an `Optional` selection, so that a corrupt value and "not selected"
are different states.

## 4. Major findings

### M1. **Two SHA-256 digests are published for one release, and neither is checkable**

`.github/workflows/build.yml:38-58` builds the bundle in the `bundle` job and uploads it as an
artifact. `.github/workflows/build.yml:60-83` is a separate `release` job that **rebuilds the app
from scratch** (`:70-71`) and packages it again (`:73-77`). Two builds of the same commit produce
two different tar archives, because `tar` embeds file modification times and the two jobs run
minutes apart. The release therefore ships a digest that belongs to a different archive than the one
the `bundle` artifact contains.

Nothing verifies the digest. `Casks/budsbar.rb:3` stores
`fb4d4b8ffaef3a4165854a2b3ead99b954f8daa415f094a567f6f594b7183bda`, and no step in the workflow
computes that value from the artifact it actually publishes. Rebuilding the same way locally yields
a different hash for the same reason.

**Impact:** `brew install --cask budsbar` can fail with "Checksum mismatch", and there is no
principled way to tell which of the published digests is the right one.

**Fix:** make the `release` job download the `BudsBar-app` artifact instead of rebuilding it, and
have one place compute the digest. See §9, S5.

### M2. **`brew install --cask budsbar` cannot work as documented**

`README.md:74-78` promises:

```sh
brew install --cask budsbar
```

The cask lives in this repository (`Casks/budsbar.rb`), not in `homebrew/cask`. Homebrew only
resolves a bare cask name from its own taps, so the command returns "No available formula or cask
found" unless the user has tapped this repository first.

**Impact:** the documented install path for the most convenient channel fails with an error that
does not mention the tap.

**Fix:** either add the tap to the instructions (`brew tap Egorich-print/budsbar && brew install
--cask Egorich-print/budsbar/budsbar`), or open a pull request against `homebrew/cask` and point the
README at the upstream cask.

---

### M3. **CI does not fetch tags, so every published artifact claims version 0.1.0**

`.github/workflows/build.yml:19`, `:43` and `:68` all use `actions/checkout@v4` with the default
`fetch-depth: 1`, which does not fetch tags. `scripts/build-app.sh:64` then runs:

```bash
VERSION="$(git describe --tags --abbrev=0 2>/dev/null || true)"
```

Without tags this fails, `VERSION` stays empty, the regex on `scripts/build-app.sh:66` does not
match, and the plist keeps its fallback values from `Resources/Info.plist:19-22` —
`CFBundleShortVersionString` `0.1.0` and `CFBundleVersion` `1`.

**Impact:** the artifact uploaded on every push, and the bundle published on every tag, report
themselves as version 0.1.0. This is precisely the bug that commit `ac3d340` ("Stamp the release
version into the bundle and update the cask") was written to fix — the fix works locally and does
not work in CI, because CI never sees the tags.

**Fix:** `fetch-depth: 0` on all three checkout steps, or read the version from the tag that
triggered the run via the workflow context instead of from git.

### M4. **A development build reports itself as a released version**

`scripts/build-app.sh:64` uses `git describe --tags --abbrev=0`, which returns the nearest
**reachable** tag, not the tag of the current commit. The current `HEAD` is `4c3d768` ("Point the
cask at v0.1.4"), one commit after the `v0.1.4` tag, so a bundle built from it carries
`CFBundleShortVersionString = 0.1.4`.

**Impact:** a build from an untagged commit is indistinguishable from the released one. If a user
reports a bug with "version 0.1.4", the version string does not identify the code.

**Fix:** use `git describe --tags --exact-match` and fall back to `<last-tag>+<short-sha>` when the
commit is not itself tagged.

### M5. **The app is ad-hoc signed and not notarized**

`scripts/build-app.sh:79-83` signs the bundle with `codesign --force --sign -` only. The result
passes `codesign --verify --deep --strict` (exit 0) but `spctl -a -vvv` rejects it, and the
signature carries `flags=0x2(adhoc)`.

**Impact:** a release downloaded from a browser is blocked by Gatekeeper on first launch ("cannot be
opened because the developer cannot be verified"), and the Bluetooth privacy grant is tied to the
signature, so the grant is unstable across rebuilds — `README.md:70-72` documents this for local
builds, but it applies to published releases too.

**Fix:** sign with a Developer ID Application certificate and notarize via `xcrun notarytool submit`
followed by `xcrun stapler staple`. See §9, S5.

### M6. **No automatic reconnection and no reaction to sleep or wake**

`Sources/BudsBar/BudsBarApp.swift:11` holds a single `didConnect` flag, and
`Sources/BudsBar/BudsBarApp.swift:16-20` calls `connect()` from the popover content's `onAppear`
exactly once. There is no `NSWorkspace.didWakeNotification` or `willSleepNotification` observer
anywhere in `Sources/`, and the flag is never reset.

`Sources/BudsCore/DeviceController.swift:82-86` treats a dropped channel as a disconnect and stops
polling, but nothing ever re-establishes the channel.

**Impact:** after the Mac sleeps, the RFCOMM link is dead and the panel keeps showing the last known
state indefinitely. The user has to quit and relaunch the app — or at minimum open and close the
popover, which does not help, because `didConnect` is already `true`.

**Fix:** observe the workspace sleep/wake notifications, reset `didConnect` on wake, and re-run
`connect()` with backoff on an unexpected disconnect.

### M7. **Values the device never reported are presented as facts**

`Sources/BudsUI/PanelContent.swift` substitutes defaults for every unknown:

| Line | Expression | What the user sees when the device said nothing |
|---|---|---|
| `:236` | `controller.state.cancellationLevel ?? 0` | "Balanced" |
| `:243` | `controller.state.equalizerPreset ?? 0` | "Flat" |
| `:250` | `controller.state.lowLatencyEnabled ?? false` | the toggle is drawn **off** |
| `:257` | `controller.state.soundQuality ?? .connectivity` | "Connectivity" |

`README.md:27-29` states the opposite: "Every setting is **read back from the earbuds** before it is
reported as applied, so the panel never shows a value the device did not accept."

**Impact:** on a model that does not answer a particular read — which the protocol explicitly
allows, since the device answers "unsupported command" (C2) — the panel shows a confident, wrong
value. The low-latency toggle is the worst case: "off" reads as a measured state, and the user may
switch it on and assume the earbuds were already in low-latency mode.

**Fix:** introduce an explicit "unknown" state and render it as such — a disabled control, a dash,
or a "not reported by this model" note. The state model already uses `Optional` for exactly this
purpose (`Sources/BudsCore/DeviceState.swift:117-126`); the UI just does not honour it.

### M8. **The volume control fails silently, and its polling fights the user**

- `Sources/BudsUI/VolumeModel.swift:78` — the result of
`OutputVolume.setLevel(...)` is discarded. A failed write is invisible.
- `Sources/BudsUI/VolumeModel.swift:24` — `isAvailable` and `:22`
`deviceName` are published but never rendered anywhere in
`Sources/BudsUI/PanelContent.swift:111-126`. The slider is shown even when no audio device was
found.
- `Sources/BudsUI/VolumeModel.swift:30-31` — the CoreAudio device is resolved
once, in `init()`. `Sources/BudsUI/PanelContent.swift:13` creates the `VolumeModel` when the panel
content is built, which can be before the Bluetooth audio device exists.
- `Sources/BudsUI/VolumeModel.swift:32-38` polls every three seconds and
`Sources/BudsUI/VolumeModel.swift:68-73` overwrites `level` from the device.

**Impact:** the slider shows a value for a device that may not exist, a failed write is invisible,
and the three-second poll can overwrite the slider position while the user is dragging it — the
classic "the knob jumps back" defect.

**Fix:** surface the CoreAudio error, re-resolve the device when the link changes, and suppress the
poll while the user is interacting with the slider.

### M9. **A refresh is 13 sequential reads with a 3-second timeout each**

`Sources/BudsCore/Commands.swift:238-252` defines 13 read requests, and
`Sources/BudsCore/DeviceController.swift:149-156` executes them one after the other. Each read has a
3-second timeout (`Sources/BudsCore/DeviceController.swift:171-177`). A command the device does not
answer therefore costs the full 3 seconds.

**Impact:** one `refresh()` can take up to 39 seconds. The 20-second poll
(`Sources/BudsCore/DeviceController.swift:92-94`) and the manual refresh button
(`Sources/BudsUI/ControlPanel.swift:302-305`) can both be running at once. Worse, a single
unanswered command produces the banner "The earbuds did not answer in time."
(`Sources/BudsCore/DeviceController.swift:215`) at connect time, which reads as a connection problem
when it is one missing feature.

**Fix:** shorten the per-command timeout, skip commands the model is known not to support, and
report per-command failures instead of one global banner.

### M10. **The panel height does not account for the error banner, and the window is found by a private class name**

- `Sources/BudsUI/ControlPanel.swift:75-86` stacks the header, the error
banner and the scroll area. The window height is computed at
`Sources/BudsUI/ControlPanel.swift:109-119` as `effectiveHeaderHeight + contentHeight`. The banner
is measured by no `PreferenceKey` — only `ContentHeightKey` (`:14-19`) and `HeaderHeightKey`
(`:22-27`) exist — so its roughly 34 pt (`Sources/BudsUI/ControlPanel.swift:236-258`) are missing
from the total and the bottom of the content is clipped whenever an error is showing.
- `Sources/BudsUI/ControlPanel.swift:126-131` locates the popover window by
looking for a content view whose type name contains `"MenuBarExtraHostingView"`.

**Impact:** the first is a visible layout bug — a clipped last row whenever an error banner is up.
The second is a latent one: the string is a private SwiftUI implementation detail, and if macOS
renames that class the panel silently collapses to the height of its header again — the exact bug
that commits `0fe0838` ("Fix the panel collapsing to the header") and `d92e8b6` were written to fix.

**Fix:** measure the banner with a third `PreferenceKey` and add it to the height sum. Find the
window by a property of the window itself (its `identifier`, or the `NSPopover` that owns the
content view) rather than by a class-name string match.

### M11. **The same error is shown twice, and the same error is shown once**

- `Sources/BudsUI/ControlPanel.swift:90-92` resets `dismissedError` only when
`controller.lastError` becomes `nil`, and `Sources/BudsUI/ControlPanel.swift:230-233` suppresses the
banner when the error text equals `dismissedError`. `lastError` is cleared only on a successful
write (`Sources/BudsCore/DeviceController.swift:221` and `:231`). Consequently a repeated failure
with the same message is never shown again — the user sees the error once and then silence.
- `Sources/BudsUI/ControlPanel.swift:77-79` renders the error banner, and
`Sources/BudsUI/PanelContent.swift:21-23` renders the same message again inside the "Try Again"
block (`Sources/BudsUI/PanelContent.swift:174-191`), because both read the same `linkState` /
`lastError`.

**Impact:** the banner and the inline block show the same sentence twice in the panel at the same
moment; and a recurring error becomes invisible after the first occurrence.

**Fix:** separate the two surfaces (banner for write failures, inline block for connection
failures), and key the dismissal on an error *id* rather than on its text.

### M12. **The capability table covers one model out of twelve**

`Sources/BudsCore/DeviceCapabilities.swift:38-56` branches on the model code and has exactly one
case, `"BTFT0020"` (FreeBuds 6). Every other model — and `nil`, i.e. an unidentified device — falls
through to `.full` (`Sources/BudsCore/DeviceCapabilities.swift:32`), which offers three modes and
four levels.

The comment at `Sources/BudsCore/DeviceCapabilities.swift:8-11` explains why: the firmware "happily
accepts any value — including modes the hardware does not implement", so the app cannot ask the
device what is supported.

**Impact:** on an unknown model the panel offers, for example, a transparency mode that the hardware
does not have. The write is accepted by the firmware and nothing happens, and the read-back reports
something different — which the app cannot interpret.

A second, duplicating model list lives at `Sources/BudsCore/DeviceState.swift:50-64` (11 model
codes). Two lists of models in two files will drift.

**Fix:** merge the two tables into one, and treat "unknown model" explicitly — offer the
intersection that every FreeBuds supports (off / cancellation) rather than the union.

### M13. **No autostart, no localisation, and the accessibility semantics are wrong**

- No login item and no LaunchAgent: no `SMAppService`, `LoginItem` or
`LaunchAgent` reference exists anywhere in `Sources/`, `Resources/` or `scripts/`. The user must
launch the app manually after every reboot.
- No localisation: there is no `.lproj` directory and no `.strings` file, and
every user-visible string is hard-coded English — `Sources/BudsUI/PanelContent.swift` (section
titles, labels), `Sources/BudsUI/ControlPanel.swift:323-335` (status subtitle),
`Sources/BudsUI/Controls.swift`.
- Accessibility: the hand-drawn switch at `Sources/BudsUI/Controls.swift:106-108`
exposes a `Toggle` through `accessibilityRepresentation`, and the file's own comment at `:85-87`
states the consequence — "VoiceOver still announces it as a checkbox". A switch that VoiceOver calls
a checkbox is a semantic error. The volume slider (`Sources/BudsUI/PanelContent.swift:117`) and the
hand-drawn segmented control (`Sources/BudsUI/Controls.swift:76-77`) carry no accessibility value of
their own.

**Impact:** the app is unusable by a VoiceOver user for the settings that are drawn rather than
borrowed from AppKit, and it is English-only in a market where the competing vendor app is
localised.

**Fix:** add a `SMAppService` login item behind a preference, move the strings into a
`Localizable.xcstrings` catalogue, and use the `switch` accessibility trait for the drawn toggle.

## 6. External cross-check: what the project is missing

### F1. **The ANC level works on FreeBuds 6 — but the two tests used different firmware, and the project's own conclusion may be right**

`docs/research/PROTOCOL.md:110-117` states that on the FreeBuds 6 "the firmware accepts the strength
byte but does not apply it", and `Sources/BudsCore/DeviceCapabilities.swift:41-52` excludes level 2
from the model's option list on that basis.

Gadgetbridge issue #7339 ("Huawei FreeBuds 6: enable noise cancelling and ANC levels", opened 15
November 2026 by Blue-Glaucus, merged into master on 16 November 2026 as commit
`311881c44e9bbc1f86cb02e822421a62d7430684`) reports the opposite, tested on real FreeBuds 6
hardware:

- The levels normal (`0x00`), comfort (`0x01`) and dynamic (`0x03`) **each
audibly change the sound**.
- Ultra (`0x02`) has no audible effect, so the patch does not offer it.
- The decisive detail is the TLV tag: for FreeBuds 6 the level is sent in tag
`0x01`; the FreeBuds Pro format uses tag `0x02`. The project writes to tag 1
(`Sources/BudsCore/Commands.swift:260-270`), so the *format* is already correct — only the
documentation and the capability table are wrong.
- The upstream maintainer merged it, and the issue also records that the
vendor app on the latest firmware does not expose ANC levels.

<https://codeberg.org/Freeyourgadget/Gadgetbridge/issues/7339>

**The two results are not directly comparable, and the difference is the firmware.** Gadgetbridge's
test ran on **HarmonyOS 6.0.0.352 (F003H003C90)**; the project's own test ran on **HarmonyOS
6.1.0.358 (F003H003C90)** — one release later, on the same model code. The maintainer's remark
that "the vendor app on the latest firmware does not support anc levels" points the same way: the
feature may have been withdrawn in a later firmware. Two readings remain open, and the project's
observation is not simply wrong:

1. The feature works on 6.0.x and was removed in 6.1.x. Then
   `docs/research/PROTOCOL.md:110-117` is correct for the firmware the project tested, and
   `Sources/BudsCore/DeviceCapabilities.swift:41-52` is right to offer only 0, 1 and 3.
2. The level is applied but the device does not echo it back in the byte the project watched. Then
   the write works and only the verification is wrong.

Note what is *not* in doubt: the write payload the project sends is byte-for-byte the payload that
was proven to work on this model. `setNoiseMode(_:level:)` writes tag 1 = `[mode, level]`
(`Sources/BudsCore/Commands.swift:260-270`), which is exactly the OpenFreebuds level-change payload
(`active_mode_value + value_byte`) and exactly the Gadgetbridge FreeBuds 6 payload
(`{0x01, level}` in tag `0x01`). The level codes agree numerically too — 0/1/2/3 in all three
implementations; only the labels differ (the project says "Balanced / Comfortable / Deep / Dynamic",
the others say "normal / comfort / ultra / dynamic").

**Impact:** the project's capability table happens to be right — `DeviceCapabilities.swift:47-51`
offers 0, 1 and 3, which is precisely the set Gadgetbridge found audible, with 2 excluded because it
has no audible effect. The *reason* recorded in `docs/research/PROTOCOL.md:110-117` is not
established, and a maintainer reading it will conclude the wrong thing about the protocol.

**Fix:** re-test the level write on the firmware the project actually ships against, capturing the
full `0x2B2A` answer before and after each level change, and record the outcome — including which
firmware version it applies to. Until then, state the finding as "the level is accepted and applied
on HarmonyOS 6.0.x per #7339; on 6.1.0.358 the project's own test observed no change in the
reported level, cause unknown". Then re-justify
`Sources/BudsCore/DeviceCapabilities.swift:41-52` on that evidence.

### F3. **The RFCOMM channel is model-dependent, and `PROTOCOL.md` states it as a protocol property**

`docs/research/PROTOCOL.md:14` presents "RFCOMM channel: 1" as a property of the protocol. It is a

**Impact:** none for this project — `Sources/BudsCore/RFCommLink.swift:133-140` resolves the channel

a reader who trusts `docs/research/PROTOCOL.md:14` will hard-code 1.

### F4. **The semantics of tag 2 in the `0x2B2A` answer are not established**

The tag-2 value in the `0x2B2A` answer carries different things in different implementations:

- The omarchy bridge requires it to be exactly `b"\x05"` and treats it as a
strict constant — anything else is `anc_invalid`
(<https://github.com/filipechagas/omarchy-huawei-freebuds>).
- freebuds-client records it as `00` in its FreeBuds Pro 5 captures, and does
not interpret it (§4.2, §7).
- The project reads it as nothing at all
(`Sources/BudsCore/DeviceController.swift:277-281` uses only tag 1).

**Impact:** none today, because the project ignores the field. It becomes relevant the moment tag 2
is used — for example to distinguish the transparency sub-mode, which freebuds-client reads from tag
2 when the mode is awareness.

**Fix:** capture the tag-2 value on a live device across all three modes and record what it means
before relying on it.

## 7. macOS-side facts found by reverse engineering

These are not project defects; they are platform facts established during the review, all of which
were re-verified directly on this machine.

### The codec line format

The Bluetooth daemon writes the negotiated codec into the system log in a fixed format. The format
strings were located in the dyld shared cache — the daemon itself is not a separate file on disk
(`/usr/libexec/bluetoothd` does not exist), and `/usr/libexec/bluetoothuserd` is present as a
distinct helper:

```
/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/dyld_shared_cache_arm64e.09
```

All seven format strings were found in that file during this review:

| String | Meaning |
|---|---|
| `, BtRt %u Kbps` | bitrate |
| `, Codc %s` | codec |
| `, Freq %s` | stream frequency |
| `, DvNm '%@'` | device name |
| `, JtBf %.0f ms` | jitter buffer |
| `, NsFl %d` | — |
| `, RtmR %.0f%%` | — |

The codec names in the same image are `AAC-LC`, `AAC-ELD`, `CVSD` and `MSBC`.

### Consequence for the project

**The stream frequency is available and the project does not parse it.**
`Sources/BudsCore/AudioCodec.swift:143-153` (`parseLine`) extracts only `Codc`, `BtRt` and `DvNm`.
The same log line carries `Freq %s` — the actual frequency of the running stream.

`docs/research/PROTOCOL.md:41-42` does not claim this, but `README.md:41-42` and
`docs/architecture/DESIGN.md:97-99` both state that the sample rate comes from CoreAudio. In
practice the app reads `kAudioDevicePropertyNominalSampleRate`
(`Sources/BudsCore/OutputVolume.swift:252-264`, called from `Sources/BudsCore/AudioCodec.swift:91`
and assigned at `:108`) — the *nominal* rate of the device, not the frequency of the stream that is
playing right now.

**Fix:** parse `Freq %s` from the same log line and prefer it over the nominal rate; fall back to
CoreAudio when the line is absent. This is a strict improvement and costs a single regular
expression.

### The controller line versus the device line

On a live macOS 27.2, the daemon's `GetControllerInfo` string is written for the **controller**,
e.g. `BlSt PoweredOn, DcsS Off, Chip BCM_4388C2, …`, and it does **not** contain `BtRt`, `Codc` or
`DvNm`. Those fields appear in the per-device line, which is written only when the device is
connected as an A2DP sink.

On this machine the FreeBuds 6 are paired but not connected (`system_profiler SPBluetoothDataType` →
"Not Connected"), so no per-device line was produced. This is the direct reason the codec line
cannot be verified end to end here.

`Sources/BudsCore/AudioCodec.swift:95` uses `system_profiler` purely as a trigger, and `:101-103`
reads the log back with `log show --last 20s`. That 20-second window is tight: the line must be
newer than 20 seconds when the log is read. The two attempts at `:99-106` sleep 120 ms and 400 ms
respectively, which is short if the daemon writes on a slower cadence.

### There is no public API for the codec

A reverse-engineering pass over `/usr/libexec/bluetoothuserd` (arm64, sha256
`c6215289b1fe93e8cde7bb09f934c92c6ac75edb5b884bd29e0209b95a78dc69`, re-verified during this review)
found an XPC surface `com.apple.bluetoothuser.xpc` with the methods
`getControllerInfoForDevice:completion:`, `storeControllerInfo:completion:` and
`deleteControllerInfoForDevice:completion:`. All three names, the XPC service name and the string
`AACP` (Apple Audio Codec Protocol) are present in the binary.

No public API returns the negotiated codec, so the system log remains the only source. The current
approach is justified.

### The fork

`felipecastro009/budsbar` forked this repository on 13 November 2026, added 16 commits on top of
`4c3d768`, and published release **v0.2.0** with a signed-but-ad-hoc `BudsBar-0.2.0-arm64.dmg`.
It is a real fork with real work, not a copy: native AppKit controls replace the hand-drawn ones, the
menu-bar glyph became a monogram, `Sources/BudsUI/Motion.swift` (325 lines) was deleted, CI moved
to macOS 27.2, and support for the **HUAWEI FreeBuds Pro 5** (`BTFT0023`, firmware
`HarmonyOS 7.0.0.350`) was added with a screenshot of the panel running against it.

Three observations matter for this report:

- **The fork independently fixed C8.** `Sources/BudsCore/WireFormat.swift` in the fork changes
  `byteList` from `value.map { Int(Int8(bitPattern: $0)) }` to `value.map(Int.init)` — the exact fix
  proposed in C8 — and adds `Tests/BudsCoreTests/FreeBudsPro5Tests.swift` asserting that an
  advertised `255` stays `255` through a write. The finding is confirmed by practice.
- **The serial travelled with the fork.** The fork replaced the hard-coded value in
  `Sources/BudsPanelShot/main.swift` with `PREVIEW-DEVICE`, but the three PNGs under
  `docs/images/` were inherited unchanged, and the fork's history still contains the original
  commits (`6f5bac0`, `0fe0838`, `34d6cf3`, `3c01b9e`) with the serial in them. The published DMG
  does not contain the serial — the string is absent from the binary. So rewriting *this*
  repository's history (S1-A) no longer removes the data from the public internet; it only stops
  the origin from being a source of it.
- **The fork is on a newer firmware than this project.** Pro 5 on `HarmonyOS 7.0.0.350` is a later
  release than the FreeBuds 6 on `HarmonyOS 6.1.0.358` this review could test, which makes the
  fork's device a candidate for the live measurement session S2-B calls for.

The fork has not opened a pull request or an issue against this repository, and its CI does not
reference it, so there is no direct risk to the original from the automation.

### S3. Make the transport and the coroutine usage sound

| Option | What | Pros | Cons | Risk | Effort |
|---|---|---|---|---|---|
| **A — token-based correlation** | Give every request a token, stored in `PendingRequest` and in the waiter entry; make each timeout task remove *its own* entry by token instead of `removeAll { $0.command == ... }` (`Sources/BudsCore/DeviceController.swift:167`); wait for the write command id (`:196`); add a timeout around `openRFCOMMChannelAsync` (`Sources/BudsCore/RFCommLink.swift:154-171`); close the channel in `deinit` | Fixes C3 and C4 with a contained diff in one file; no user-visible behaviour change | Does not fix the 39-second refresh or the sleep/wake problem | Low | 4–6 h |
| **B — A plus a serialised request queue** | Replace the ad-hoc `pending` array with an actor owning a FIFO queue, one request in flight, correlating strictly by order; reconnect with backoff on an unexpected disconnect; observe `NSWorkspace.didWakeNotification` | The concurrency model becomes auditable; reconnect-on-wake disappears; the slow refresh becomes a visible queue-depth problem rather than a timing accident | A rewrite of `DeviceController`'s request handling; needs a new test suite with a fake transport | Medium | 1.5–2 days |
| **C — B plus per-command timeouts and capability-driven skipping** | Shorten the read timeout to ~1 s, skip commands the connected model is known not to support, report failures per command instead of as one banner | The refresh becomes fast; the error messages become specific | Needs an accurate capability table first — S2 and M12 must land first | Low once the table is right, medium if it is not | +0.5 day |

**Recommendation: A now, C after S2.** B's queue is the right end state but should not start before
the tag semantics are settled, or it will be written against a protocol model that is about to
change.

### S6. New protocol features

Priority order, by user value per unit of work.

| Priority | Feature | Commands | Effort | Note |
|---|---|---|---|---|
| 1 | In-ear detection | `0x2B03`, `0x2B25` | 3–5 h | The most-used feature of the vendor app. The read-back layout is known from OpenFreebuds |
| 2 | ANC change push | `0x2B03` / spontaneous `0x2B2A` | 2–3 h | Removes the 20-second polling delay for the most-used control. Requires the correlation work from S3 |
| 3 | Auto pause / wear detection, with UI | `0x2B11` / `0x2B10` | 3–4 h | The protocol half already exists in `Sources/BudsCore/Commands.swift:205`/`:219`; only the UI is missing |
| 4 | Noise-cycle write | `0x2B18` | 2 h | Declared but never sent; needs a live confirmation of the payload |
| 5 | Swipe write | `0x2B1E` | 2 h | The read exists; freebuds-client deliberately kept the write read-only, so the payload must be captured first |
| 6 | Capabilities command | `0x2BAC` | 2–3 h | Declared, never requested; would replace the hard-coded capability table (M12) with device-reported data |
| 7 | Pinch and hold | `0x2B93` / `0x2B92` | 4–6 h | Only on models that have the gesture |
| 8 | Audio multiplexer | `0x2BB4` | 1–2 days | Spatial audio, adaptive volume, conversation recognition, ANC with one earbud, head control — five features, each a subcommand |
| 9 | Service language | `0x0C02` / `0x0C01` | 3–4 h | The layout is known from OpenFreebuds; the locale list lives in tag 3 |
| 10 | Dual connect per device | `0x2B31`–`0x2B36` | 1–2 days | The enable/disable flag is already read; the device list and the per-device priority are not |

**Do not start 7–10 before 1–6.** The correlation work in S3 is a prerequisite: without it, a push
notification arriving during a read will be consumed by the wrong waiter — the same defect as C3, on
a channel that is busier.

## 10. Suggested order of work

1. **S1 — purge the serial from the repository and from the PNGs.** `git filter-repo` over the full
   history, force-push, request the GitHub cache purge, regenerate all three PNGs with a synthetic
   serial, replace the fixture frame, and delete the local `backups/` copies from disk. Then ask the
   owner of `felipecastro009/budsbar` to regenerate their PNGs and rewrite their history too — the
   rewrite above alone no longer unpublishes anything. Everything else is reversible; this is not.
2. **S2-C7 — request tag 9 and read the serial.** `Commands.swift:239` and
   `DeviceController.swift:312-325`. One line in the request removes a dead UI field; it also
   unblocks the honest "Serial" row in the panel.
3. **S2-C8 — make `byteList` unsigned.** `WireFormat.swift:66-70` and the `-1` sentinel at
   `ControlPanel.swift:426`, `:434`. The fork `felipecastro009/budsbar` has already made this change
   and added a test for it (§7) — take the fix and the test from there rather than writing it again.
4. **S2-C5 — correct the ANC documentation and verify the level byte.** `DeviceController.swift:242-245`
   plus `PROTOCOL.md:88` and `:106-117`. The decoding is already correct and agrees with three
   independent implementations; the notes are not, and the write path verifies the mode but never
   the level it just wrote.
5. **S3-C3/C4 — correlate by token and wait on the write id.** `DeviceController.swift:101-180`,
   `:196`. The remaining protocol defects cannot be diagnosed reliably until a wrong response can
   no longer be consumed by the wrong request.
6. **S2-C2 — decode tag 127.** `Commands.swift:227-234` and `DeviceController.swift:101`. Once
   the write answer is correlated correctly, the refusal marker becomes visible and the timeouts
   disappear.
7. **S2-C6 — read the charging flags from tag 3.** `DeviceController.swift:333`, confirmed against
   a charging device. Cheap, but it needs the device.
8. **S5-A — make CI produce correct artifacts.** `build.yml:19,43,68` and `:60-83`,
   `build-app.sh:60-77`. `fetch-depth: 0` is one line and fixes the version stamped into every
   published bundle.
9. **S4-A — stop inventing values in the UI.** `PanelContent.swift:236-260`,
   `ControlPanel.swift:109-131`, `VolumeModel.swift:78`. This is the difference between the panel
   and `README.md:27-29` telling the truth.
10. **S2-B — a live measurement session.** With the earbuds connected, capture the `0x2B2A`,
    `0x0108`, `0x2B04` and refusal frames and publish the table in `PROTOCOL.md`. This closes F1,
    F4 and the remaining open questions in one pass, and it is the precondition for S6. The fork's
    FreeBuds Pro 5 on `HarmonyOS 7.0.0.350` is a newer firmware than the one this project was
    tested on, which makes it a good candidate for the capture.
11. **S5-B/C — sign, notarize, and make the cask installable.** `build-app.sh:79-83`,
    `Casks/budsbar.rb`, `README.md:74-78`.
12. **S3-B/C and S6 — reconnect on wake, then the new features.** Only after steps 5 and 10: the
    push-notification features depend on a correct correlation model, and the
    capability-driven skipping depends on accurate measurements.
